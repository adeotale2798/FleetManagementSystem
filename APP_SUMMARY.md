# Fleet Manager — app summary

## Why this app exists

Fleet Manager is transport-office software for moving a logistics business's day-to-day work out of disconnected paper, spreadsheets, and manually reconciled cash records. It brings trips, lorry receipts (LRs), fleet and people, collections, expenses, and business reports into one operational workflow. Its financial balances are calculated from recorded transactions rather than maintained as hand-entered totals.

The product began as a focused tool for a local transport business. The current implementation also supports a platform operator issuing licences to multiple independent businesses. Each business uses the same application while its operational records remain in its own MongoDB database.

## Who uses it

- **Business owner (`owner`)**: operates only the Booking and Industrial sections granted to that login by the platform owner, within the business's licensed modules. Each business retains its own tenant data.
- **Site manager (`site_manager`)**: sees only Dashboard, Receipts and Ledger for explicitly assigned active sites; trip, receipt, charge and export actions follow per-site grants. Site managers are denied access to industrial business routes.
- **Platform owner (`superadmin`)**: creates and manages business licences and subscription plans, activates/suspends businesses, resets owner passwords, sets customer-specific subscription entitlements and reference prices, assigns each business admin's section grants, views platform activity/error summaries, configures Booking setup for every client, and can enter a separately audited full-access support session for a selected customer's app.

Platform administration is not a tenant business role. A normal platform login has no tenant association and can only access platform routes. A separately issued support token creates an ephemeral tenant-bound owner-compatible principal for one selected client; it does not change the platform user's stored account or the customer's saved admin permissions.

## What it does today

| Area | Purpose and principal workflows |
|---|---|
| Booking Dashboard | Default booking screen at `/booking/dashboard`: choose a date, create an open trip with optional vehicle/driver details, and select a trip card showing its number, assignment and receipt count. |
| Booking Receipts | `/booking/receipts`: create, edit and print receipts within the selected trip without re-entering its vehicle/driver. Data entry and editing stay in English; owner-configured Hindi conversion is used for Hindi good, description and quantity output. Owners can choose receipt print language and independently show/hide sender and receiver addresses per site. Receiver phone is retained and printed. The configurable receipt fee is stored on each receipt. Three goods rows appear by default; each supports a good, optional description, quantity, Bhada and Hamali. Editing offers a cancel action that discards unsaved form changes. The branded single-page A4 print shows Hindi goods/descriptions/quantities inline, charges and total, and the server-recorded creation time in IST. |
| Booking Ledger | `/booking/ledger`: select one trip for a date and display its receipts in a plain spreadsheet-style table. Sender, receiver and comma-separated Hindi good/description/quantity entries are read-only; only Bhada and Hamali can be edited with autosave through the audited site-LR API. The recorded receipt fee is displayed as read-only. Creator attribution shows Admin or Manager and their name. Print and `.xlsx` export are limited to the selected trip and use Hindi goods/descriptions/quantities. |
| Booking Finance | Owner-only `/booking/finance`: all active site receipt Bhada/Hamali totals, configurable receipt fees, combined grand total, posted collections, outstanding balances (including receipt fees) grouped by receiver and reconciliation counts. Owners can settle a receiver's remaining Bhada and receipt fees and record promised payment dates and follow-up notes; Hamali is not classified as collected money. |
| Booking Audit | Owner-only `/booking/audit`: pending/unpaid receipt review, promised payment follow-ups and site audit history with actor, time, reason and before/after values, including receipt restore and settlement actions. |
| Booking Setup & Access | Owner-only `/booking-setup`: create/edit sites, preview/confirm legacy assignment, assign Office Team managers, manage site permissions, reset/deactivate manager logins, and configure booking categories. Site managers are selectable from active Team profiles with manager roles; owners can add a missing profile inline. A selected Team profile is linked to a distinct site-manager login by ID; credentials stay out of Team records. Permission controls are grouped and described in plain language. Temporary passwords are shown only after assignment/reset; passwords are hashed and cannot be retrieved later. |
| Sites & managers | Managers have tenant-scoped platform login accounts and explicit site permissions. Creation and update metadata and site audit events retain the acting login ID and timestamp; audit history is owner-only and creator metadata is omitted from manager responses. Keep manager IDs/status/site access in the setup register; securely reset credentials and revoke assignments when replacing/deactivating. Authorized managers see only their site assignments. |
| Site trips & receipts | Timezone-based trip references and atomic sequences; optional vehicle/driver; trip close and owner-only audited reopen; server-generated receipt numbers; multiple goods rows with original/Hindi text; optional addresses; idempotent retries and site-scoped audit history. |
| Site finance compatibility | Historical payment, reversal, reconciliation and trip-expense APIs remain for existing records and shared finance consumers. The simplified booking pages do not expose old reconciliation workflows. Bhada/Hamali are Decimal-validated independently; total rent is their server-derived sum. |
| Site trip expenses | Auditable trip-linked expense recording and display using the established shared ledger/cashbook posting model, with every booking posting tagged to its site. |
| Industrial Trips & LRs | Owner-only large industrial shipments: indoor routes or outdoor addresses; trip assignment, cost/profit view, industrial LRs with freight and consignor/receiver details, and receipt status. Site booking trips and LRs are not shown or edited here. |
| Vehicles | Fleet records, status, documents/expiry, vehicle history, and fuel/expense context. |
| Parties | Customer records, receivables, party ledger, LRs, and collections. |
| Team | Drivers and office team, profiles, advances/repayments, and Deewanji collection handovers. |
| Industrial Finance | Owner-only industrial receivables/payables, collections, cashbook, expenses, fuel, payments, advances, Deewanji, and third-party logistics (3PL). Site-tagged bookings, expenses, ledger rows and cashbook rows are excluded. |
| Industrial Reports | Owner-only date/search-filtered industrial reports with CSV, Excel-compatible, PDF, and print exports; site booking records are excluded. |
| Settings | Company/branding, locations and routes, numbering, due days, opening balances, categories, payment modes, and partners. |
| Platform control | A modern searchable client directory opening on Needs attention, with recommended next actions and All customers one tap away, plus a dedicated Renewals queue for licences due within 30 days or already expired; every renewal row opens the selected customer's subscription editor directly. Plans & pricing and Platform settings are separate. Attention cases include suspended or expiring/expired licences, no saved plan, or no active admin. Customer workspaces show an Active → Expiring soon → Expired lifecycle (with Suspended called out separately), alongside Overview, Subscription, Users & access, Booking setup, and customer change history; user access opens on an active business-admin login where possible, and per-user counts reflect only entitlements effective under both plan and licence. The subscription editor is viewport-contained, scrolls its content independently, and separates plan/renewal details from included sections. Access can start from an all-included-for-this-plan preset or reusable Booking operator / Finance only profiles with a preview of the sections they grant, then be refined in collapsed module groups before saving. Profile permissions outside the subscription are reported and stay disabled. Renewal opens the existing manual expiry editor; suspensions require confirmation. The plan catalogue includes Booking Essentials, Booking Complete, Industrial Modules and Full Operations starter templates with optional display-only INR prices. Per-customer subscription snapshots cap per-admin grants. Customer history translates changed subscription/access sections and reports how many admins were actually restricted; platform-wide events are labeled separately from customer events. Payment collection remains disconnected. Each selected customer also has an Open client app action that starts full-access platform support without changing that customer's saved plan or administrator grants. |

### Platform-managed Booking setup

From any selected customer workspace, the platform owner can configure Booking settings, sites and site-manager access regardless of the customer's own Booking Settings grant. The support workspace covers business-wide receipt visibility, site identity/status, receipt print options and branding, receipt-name suggestions and categories, manager assignments and per-site permissions, account deactivation, and password resets. Existing tenant data and site-operation/audit paths are reused; each manager remains tenant-scoped and a new manager's generated temporary password is displayed once. Customer admins retain their own permissions and can continue to manage Booking setup. Fee tracking and billing are intentionally not included.

### Full platform support mode

The customer workspace's **Open client app** action requires confirmation and starts a two-hour support session for that selected tenant. The app uses the normal Booking and Industrial screens with full view/edit rights, even if the customer's licence is suspended or a module is outside the subscription. This does not edit or expand any customer admin grant or subscription. The signed token is scoped to the platform owner's account, tenant and session; only that tab stores it, the backend checks the revocable session on each request, and platform administration endpoints remain unavailable while support mode is active. The persistent platform login is retained separately. A clear support banner and **Exit client** action end/revoke the support session and return to Platform Control. Session start/end and each successful support-mode write (HTTP method and route, without request-body data) appear in the customer's change history. All reads and writes use the normal authenticated tenant database context.

## Important business rules

1. **Tenant and workflow boundaries:** licence/user records are in the platform database; each business resolves to its own tenant database. Within that tenant, industrial trips/LRs (`trips`, `lrs`) and site bookings (`site_trips`, `site_lrs`) remain separate canonical record families.
2. **Financial source of truth:** `ledger` holds entity debits/credits; `cashbook` holds cash, bank, and Deewanji movements. Site postings carry `site_id`; industrial balances, reports and expense reads exclude site-tagged rows. Site booking totals use site-scoped booking/payment/expense data. UI balances are derived, with settings opening cash/bank added where appropriate.
3. **No destructive transaction cancellation:** cancellation marks a source transaction and its ledger/cashbook postings as cancelled; it retains the historical records.
4. **Trip and LR revenue:** trips and LRs can relate to the same freight. Dashboard monthly revenue avoids counting trip-linked LR freight twice.
5. **Role and section boundary:** industrial business endpoints require an `owner` and the matching per-admin grant; Booking Finance, Audit and Settings use separate grants, while Booking Dashboard/Trips/Receipts/Ledger share one grant. Site operations still enforce site/action scope for site managers. Site managers are also denied Booking APIs if Booking is absent from the tenant subscription. Platform endpoints require `superadmin`. Platform users do not inherit business-owner access except through the explicit, short-lived, tenant-scoped support token; normal platform tokens cannot call business-owner endpoints.
6. **Subscription and admin grant boundary:** reusable plan templates are stored in the platform database; each tenant stores its assigned entitlement and optional reference-price snapshot. A customer's plan snapshot caps the per-owner `admin_access` grant, enforced in the frontend and backend. Reassigning a tighter plan clamps current owner grants; later template edits do not change existing customers. Switching a customer's subscription to Custom starts with no included sections, and the subscription editor has a Clear all sections action; entitlements can then be granted individually. Legacy tenants without a subscription map retain old access behavior until explicitly assigned a plan or cleared through the editor. New business admins start with all grants disabled; unknown owner API routes are denied until classified. Reference prices are not billing records and do not collect payments.
7. **Indirect data boundary:** navigation and direct page routes are not the sole controls. Backend APIs filter global search results, dashboard aggregates and trip detail fields by the same per-admin grants, including trip amounts and costs that require Industrial Finance.
8. **Site isolation:** site records live in the authenticated business's existing MongoDB database and carry `business_id`/`site_id`; every site API checks those values and the current user's assignment/action grant. Cross-site manager access is opt-in.
9. **Historical ownership:** creator and payment events are append-only audit facts. Replacing a manager revokes access without rewriting historical identities.
10. **Manager credentials and identity:** platform user records store hashes only. New manager passwords use SHA-256 pre-hashing with bcrypt, and legacy bcrypt hashes remain supported. Manager passwords require a non-empty value but have no configured minimum/maximum password-length policy; short passwords remain easy to guess. Owner manager lists never return password fields; a temporary password is held in the browser page only after assignment/reset and must be copied securely at that time. A manager account may reference an Office Team record by `team_member_id`; it remains a separate login identity. Reset credentials to replace a forgotten password.
11. **Reconciliation:** uploaded ledgers are versioned CSV templates matched by immutable LR ID plus business/site/trip scope. Preview is validated before application; deterministic staged effects, unique financial posting references and row progress make retries safe. Missing LRs require explicit acknowledgement and remain unreconciled.
12. **Financial meaning:** bhada and hamali are recorded separately from actual payment events. The receipt's customer-facing total is derived as bhada + hamali; neither charge is treated as a payment received.
13. **Legacy data:** legacy records without a site are not silently assigned. The owner first previews the unassigned counts and explicitly confirms a repeatable assignment to the designated default site.
14. **Operation feedback:** mutating requests give users clear success/failure feedback; unexpected server errors have a reference identifier and a sanitized platform error-log record for super-admin investigation.
15. **Booking compatibility:** the redesigned screens reuse `site_trips` and `site_lrs`; historical goods/container fields remain readable. Hindi text, optional addresses, goods rows and receipt request idempotency are additive. No historical records are migrated or removed.

## Presentation system

The frontend uses a light, brand-preserving design system: forest green and its existing shades for primary actions, amber for financial attention, and neutral layered surfaces. Shared CSS variables and Tailwind mappings cover brand, canvas, surfaces, text, borders, focus and elevation. The responsive booking workspace contains Dashboard, Receipts and Ledger; industrial Trips, LRs, Finance and Reports remain separate. Booking receipt totals are derived from bhada plus hamali by the backend. Successful changes update canonical records; active data views refresh from the API after a tenant-scoped live revision changes, including across signed-in devices, without requiring a browser reload. Motion is reduced when the user requests reduced motion. This is a CSS/SVG/chart-based visual treatment, not a 3D rendering engine.

## Current boundaries (do not imply these are complete features)

- GPS live tracking is implemented as a per-vehicle WheelsEye API lookup and requires a token on each vehicle; it is not a built-in fleet tracking service.
- Google Maps address autocomplete and map pinning require `REACT_APP_GOOGLE_MAPS_API_KEY`; plain address entry remains available without it.
- Uploads are stored on the backend's local disk (`backend/data/uploads/`), so production deployments need an explicit persistence/backup strategy.
- This is a single FastAPI service with most API routes and business orchestration in `backend/server.py`; it is not a set of independently deployed services.
- Booking and industrial workflows are separate within one tenant database, not separate MongoDB databases. Site expenses use the existing `expenses` collection with `site_id`; ledger/cashbook postings are likewise tagged and must be filtered from industrial read models. Shared vehicle/driver/party masters remain common by design.
- Per-tenant feature flags and per-admin section grants are checked at frontend and backend boundaries. Legacy business-owner accounts with no `admin_access` field intentionally remain unrestricted for compatibility; the platform owner should configure those accounts.
- New site-ledger originals are stored beneath the existing private local upload store and are blocked from the legacy unauthenticated file route. Production still needs durable private storage, backups, and multi-instance deployment configuration.
- The site booking ledger downloads a formatted `.xlsx` workbook; older reconciliation templates and daily finance exports remain CSV contracts. Hamali is not integrated into profit/cash-flow reporting.
- Existing integration tests expect a running configured service and some tests mutate tenant/trip records; inspect their host/data target before invoking them. `backend/tests/test_site_ops_units.py` is offline and uses synthetic data.
